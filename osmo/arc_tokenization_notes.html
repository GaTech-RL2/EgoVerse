Arc-Length Action Tokenization

Working notes · EgoVerse / arc-length-nv-eval · results current as of the runs listed in §7

Behaviour-cloning policies normally predict actions on a time grid: N control steps ahead, uniformly spaced in seconds. This note evaluates re-parameterizing that chunk by distance travelled instead — the model predicts M waypoints spaced uniformly in arc length, plus a velocity token that restores timing at deploy. The hypothesis, the method, what was measured, and — importantly — what is still unresolved.

1 · Hypothesis

Time-indexed chunks spend their capacity uniformly in time, so a slow segment and a fast segment get the same number of predicted values despite covering very different amounts of motion. Arc-length parameterization spends capacity uniformly in space. Three claims follow:

  • H1. Arc parameterization should help most where velocity varies most. Human demonstrations vary more than scripted teleop, so the gain should be larger on human data than robot data.
  • H2. Separating path from timing (waypoints + a velocity token) should make the path easier to learn, since the model no longer has to encode speed in the geometry.
  • H3. For a hand, progress should be measured over all joints, not just the wrist: a grasp closes the fingers while the wrist is still, and a wrist-only clock assigns it no progress.

2 · Method

Given a trajectory x_0..x_T and a step distance δ, define cumulative arc length s_t = Σ δ(x_τ-1, x_τ). A token stores M waypoints sampled uniformly in s over [0, D], plus a velocity v. Reconstruction interpolates the waypoints at s(t) = v·t.

Choosing the distance

For a hand with 21 keypoints the per-step displacement is a vector d = (‖Δp₁‖, …, ‖Δp₂₁‖); the scalar step is a norm of it. The pose metric proposed as a starting point, Σᵢ[‖p̂ᵢ−pᵢ‖ + μ(Rᵢ,R̂ᵢ)], is the L1 case.

μ(R,R̂) = ½‖(RᵀR̂)1/2 − I‖F = √2·sin(θ/4)    // verified to 5 dp; a true metric (0/3000 triangle violations)
λ = 2√2·r    // makes λμ the arc traced at radius r — so λ is "how far from the pivot do I care"

Hybrid two-stream

The final variant parameterizes eef (wrist, head frame → global motion) and keypoints (21 joints, wrist frame → pure hand shape) independently: each stream gets its own D and its own distance function, both resampled to a shared M. Independent parameterization would desynchronize the streams — waypoint k is a different time in each — so reconstruction emits only the window where every stream is still inside its token:

Hvalid = mins ( Ds / vs )    // degenerate (v≈0) streams excluded; they hold their first waypoint

3 · Reconstruction analysis (before any training)

How faithfully can a token be reconstructed at all? This bounds everything downstream and is cheap to measure, so it came first.

3.1 Error depends only on waypoint spacing

Reconstruction error is a function of h = D/(M−1) alone — verified to three decimals across an 8× range of D. That decouples the two knobs: D sets the horizon, h sets fidelity, M follows.

Fig 1 — mean per-keypoint reconstruction error vs waypoint spacing. The dashed line marks the ~1.2 mm tracking-jitter floor; below it you are fitting noise.

3.2 The error is jitter-limited, not curvature-limited

Chord-vs-arc geometry predicts error ∝ h² — a 4× drop per doubling of M. Measured ratios converge to 2×, i.e. error ∝ h, with err ≈ 0.137·h.

Fig 2 — measured error vs M (points) against ideal quadratic scaling (dashed). The gap is the signature of a path that is not smooth at these scales.

Fig 3 — measured path length collapses under subsampling (coastline behaviour): 92% at 100 ms, 33% at 1.33 s. Fingertip and wrist degrade identically, so this is global tracking jitter, not finger articulation. Low-passing at 167 ms restores quadratic scaling and cuts error 3.2×.

Consequence. A large share of the "distance" being integrated is measurement noise, so tokens partly advance on jitter, and adding waypoints has diminishing returns much sooner than the smooth-curve model suggests.

3.3 Which norm

At equal token budget, all norms give near-identical mean error — they separate only in the tail, which is exactly where a resampling scheme should be judged.

Table 1 — equal token budget (276 tokens), M=15, one 94 s episode.

L∞ is the principled choice. "Advance once any joint has moved D" bounds per-joint resampling error by D, which is what a tokenizer is for. It roughly halves worst-case error vs wrist-only (16.87 → 9.11 mm) and keeps D in interpretable metres. L1 — the form in the original pose metric — inflates path length 22.6× because joints move coherently, so it needs D≈4.5 m to emit a comparable token count.

4 · Comparing two action spaces fairly

The trap. A time-indexed 100-step chunk and a D=0.20 m arc token cover different amounts of motion — measured 0.669 m vs 0.183 m, a 3.66× mismatch. Raw per-timestep MSE therefore scores them over different distances. On human data this alone produced an implausible "130× better" reading for arc-tok that collapsed to ~8× once corrected.

arc_matched_resample resamples both models' output to M points spaced uniformly in arc length over the first D metres, per arm, then compares. Verified: 1.887 m vs 0.188 m becomes 0.1878 vs 0.1874 m over 15 matched points. It is timing-blind by construction — it measures path geometry at matched distance, so velocity must be evaluated separately.

5.1 Cartesian (wrist) action space, cotrained on robot + human

Table 2 — best checkpoint per model, arc-matched (same 0.20 m, 15 points).

Supports H1. Arc-tok is a tie on robot teleop (1.04×, arc-tok ahead at the final checkpoints) and ~8× better on human data. That is the predicted pattern: arc-length resampling normalizes velocity-profile variation, and human demonstrations have far more of it than scripted teleop. Note also that the baseline barely improves on human at all across 2000 epochs.
Aside — the eva metric under-reports what the videos show. On robot teleop the arc-matched number is a near-tie (1.04×, arc-tok ahead only at the final checkpoints), which reads as "no effect". The rendered validation videos disagree strongly: arc-tok rollouts look qualitatively much closer to ground truth than the baseline's, and the gap is obvious by eye in a way a 4% metric difference is not.

That divergence is itself a finding, and it points at the metric rather than the models. Arc-matched MSE averages squared error over M waypoints, so it is dominated by the bulk of the chunk where both models are fine, and it is timing-blind by construction (§4). Failure modes that are visually glaring — stalling partway, overshooting the endpoint then correcting, moving through roughly the right region at visibly wrong speed — are exactly the ones a distance-matched average washes out. The practical read: do not conclude "no effect on robot data" from the eva number alone. Endpoint error, timing error against the velocity token, and per-waypoint error distributions (not the mean) are the measurements that would confirm or kill what the videos suggest, and none of them have been run.

5.4 Hybrid two-stream

M decouples from horizon: error scales as Ds/(M−1) per stream while Hvalid depends only on D/v, so raising M refines every stream at no cost to horizon.

Table 4 — hybrid reconstruction vs M at fixed D_eef=0.45, D_kp=0.41.

On this data the two streams move at similar rates (eef path 48.71 m vs wrist-frame keypoint L∞ 44.51 m, so D_kp ≈ 0.91·D_eef), and the hybrid's measured horizon equals the scalar L∞ horizon exactly — the fastest stream sets it either way. The hybrid should pay off where streams genuinely decouple (static wrist, fast fingers); folding is transport-dominated and does not exercise that.

6 · Pseudocode

6.1 Single stream (the base case)

Everything else is a generalization of this. Given a chunk and a step distance, walk the cumulative arc length and resample it uniformly.

TOKENIZE(x[0..T-1], D, M, dist):
    # 1. cumulative arc length under the chosen distance
    s[0] = 0
    for t in 1..T-1:
        s[t] = s[t-1] + dist(x[t-1], x[t])

    # 2. how far do we actually get? (short chunks may not reach D)
    reach = min(D, s[T-1])

    # 3. M waypoints spaced uniformly in DISTANCE, not time
    targets   = linspace(0, reach, M)
    waypoints = interp_rows(x, s, targets)        # linear in s

    # 4. velocity restores timing at deploy
    n_steps = searchsorted(s, reach)              # control steps consumed
    v       = reach / (n_steps * dt)              # metres per second

    return concat([v_row(v), waypoints])          # (M+1, dim)


DETOKENIZE(token, H, dt):
    v, waypoints = token[0], token[1..M]
    s_of_t = [min(v * i * dt, D) for i in 0..H-1] # clip: never extrapolate
    return interp_rows(waypoints, linspace(0, D, M), s_of_t)

Two details that matter. reach handles chunks near the end of an episode that never travel D — they resample over what exists rather than padding. And the clip in DETOKENIZE is what keeps reconstruction interpolating strictly inside the stored waypoints; without it a fast rollout walks off the end of the token.

6.2 Two streams (eef + keypoints, the hybrid)

The specific case in §5.4. Each stream gets its own D and its own distance function, both resampled to a shared M, each carrying its own velocity.

TOKENIZE_HYBRID(chunk, D_eef, D_kp, M):
    # split columns into two streams, per hand
    eef = chunk[:, wrist_cols]                    # 6 dims  — head frame,  global motion
    kp  = chunk[:, keypoint_cols]                 # 63 dims — wrist frame, pure hand shape

    # INDEPENDENT parameterization: different D, different distance
    tok_eef = TOKENIZE(eef, D_eef, M, dist = translation + lambda * rotation)
    tok_kp  = TOKENIZE(kp,  D_kp,  M, dist = L_inf over 21 joint displacements)

    return concat([tok_eef, tok_kp], axis=cols)   # shared M, so they stack


DETOKENIZE_HYBRID(token, dt):
    # each stream advances at its own rate, so they DESYNC after H_valid:
    # waypoint k is a different instant in each stream
    H_valid = min(D_eef / v_eef, D_kp / v_kp)     # skip streams with v ~ 0
    H       = floor(H_valid / dt)

    return concat([DETOKENIZE(tok_eef, H, dt),
                   DETOKENIZE(tok_kp,  H, dt)], axis=cols)
Why min. Emitting past H_valid would force at least one stream to extrapolate beyond its stored waypoints. Emitting less would waste horizon. So min is not a safety margin — it is the largest window in which every stream is still inside its token, and the two streams still agree on what time it is.

6.3 Generalized to N streams

Nothing above is specific to two. Streams are (columns, distance, D) triples; add a third for fingers, a fourth for torso, and the same rules apply unchanged.

streams = [ (cols_1, dist_1, D_1),
            (cols_2, dist_2, D_2),
            ...
            (cols_N, dist_N, D_N) ]               # M is SHARED across all


TOKENIZE_N(chunk, streams, M):
    return concat([ TOKENIZE(chunk[:, cols], D, M, dist)
                    for (cols, dist, D) in streams ], axis=cols)


DETOKENIZE_N(tokens, streams, dt):
    # a stream that never moves has v ~ 0 -> D/v is infinite, so exclude it
    # from the min; it simply holds its first waypoint for the whole window
    moving = [ s for s in streams if v[s] > eps ]

    if moving is empty:                           # zero token: nothing moved
        return repeat(row_0, H)                   # hold, do not divide by zero

    H_valid = min( D[s] / v[s] for s in moving )
    H       = floor(H_valid / dt)

    return concat([ DETOKENIZE(tokens[s], H, dt) for s in streams ], axis=cols)

Three properties fall out of this, none of which need the streams to be related:

  • Independence. Each stream's D and distance are chosen for its own units and dynamics. Metres for the wrist, an L∞ joint norm for the hand, radians for a torso — they never have to be commensurable, because they are only ever compared through Ds/vs.
  • M decouples from horizon. Hvalid depends only on (Ds, vs), so raising M refines every stream at no cost to how far ahead you predict (Table 4).
  • Degeneracy is well defined. A motionless stream is excluded from the min rather than producing a division by zero, and an all-zero token holds row 0.
