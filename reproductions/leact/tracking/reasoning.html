Keep both LeAct runs. The proposed PEAR allocation is additional compute, divided equally between the existing MoE warmstart and base Qwen3.8-27B. Values below describe scenarios after qualification and allocation; they are not measured PEAR completion times.

The proposal uses 512 updates as a planning milestone, with continuation driven by coverage and learning. The calculator opens at the earlier 32-update checkpoint; select 512 to price the longer schedule.

Assumptions and arithmetic

Retained episodes = updates × 128 groups × 8 episodes. Attempted episodes divide by the retained fraction. Estimated runtime is setup plus the maximum of generation time, environment occupancy and learner time, divided by availability. Async work overlaps; inference waiting is not charged twice. GPU-hours include the whole reserved allocation.

The mixed profile reserves 8 trainer / 4 rollout / 4 simulator GPUs at 16 GPUs per run. This is a proposed layout, not a launched or qualified orchestration. The CPU profile uses 8 trainer / 8 rollout GPUs. Larger budgets scale these roles.

The editable throughput proxy is anchored to the PEAR training appendix, which reports 2,000–3,000 generated tokens/s per H100 node and about 92k generated tokens per episode. Our initial sampler concurrency is lower, so these rates may be optimistic. MoE token lengths come from existing native evaluation timings, not an on-policy PEAR pilot.
